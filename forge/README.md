# forge/

Accelerators from snax-forge's design points, one folder per design point, as SNAX-GVSoC reads them (snax-forge D134): the cluster file and one streamer file per streamer set in snax_cluster's hjson form, and `accelerator.json` (snax-forge C§17, D145), the contract, run on the installed `snax_hjson` target. A folder is the fixture of snax-forge's D134: it lets this repo's regression run a design point without snax-forge. Each is snax-forge's generator's output, checked in untouched; snax-forge's `tests/gen/test_fixture.py` writes it again and compares it byte for byte. All thirty-eight were written again by snax-forge's branch `ry/core1` (CORE1 R1, one core, snax-forge D170): `snax_forge.hjson` without the DMA core, `include/snitch_cluster_cfg.h` at one core, `main.c` with the DMA on core 0 and no barrier; every other file byte for byte as before. Before that, `dot_1_shared/` and `mvt_1_dot2_shared/` are snax-forge's branch `ry/port1` (PORT1 R2: groups sharing their streamer's movers, snax-forge D169), written by that checkout's `tests/gen/test_fixture.py`. The other thirty-six are snax-forge's branch `ry/ctrl2` (CTRL2 R2: the CSR COUNTER renamed BUSY_COUNTER and its width `counter_width` `busy_counter_width`, snax-forge D152 and D168, every other byte as at B2 R5, but a header comment rewrapped by the longer name), written by that checkout's `tests/gen/test_fixture.py`; before it, `ry/b2-2` (B2 R5: `matvec_seed/` and `matvec_seed_serial/` new, the fold's seed, a per-job port on TreeAccumulate and SerialAccumulate; `vsum/` and `rowsum_serial/` written again at B2 R5's B0, on `chisel_adder_tree` and `chisel_serial`; the other thirty-two byte for byte as at `26d211d`, B2 R4: `rowsum_2/` and `rowsum_2_padded/` new, the lane accumulator, contiguous and with the `padded_rows` layout), written by that checkout's `tests/gen/test_fixture.py` (`regenerate`), in the streamer sets form (snax-forge D157): the slot is one snax_cluster entry `snax_forge_<design>` (the platform's `accelerator_slot` and the design's name) with one streamer set per accelerator, `accelerator.json` lists the accelerators, each of its groups, and every CSR keeps its width (D152). A set's streamer CSRs come first, then its accelerator's own, packed from CSR 960; the offsets in `accelerator.json` run over all the accelerators from 0, as the shell sees them. Every design is one accelerator, so one set, but `dot_1/`, two accelerators `vmul` and `vsum` in two sets; `dot_1_enc/` is the same two units encapsulated as one accelerator `dot` of two groups (D148), the form `dot_1/` had before.

Each folder holds:

- `snax_forge.hjson`, the cluster file, named after the base platform: its source (snax-forge's base cluster `platforms/snax_forge_cluster.hjson`, from snax_cluster's `cfg/snax_alu_cluster.hjson`, its names snax-forge's, the sparse interconnect, one core holding the slot and the DMA, snax-forge D170) with the platform's values written back, the cluster renamed `snax_forge_cluster` (`name` and its entry in `bender_target`) and the core's only slot set for the design: `snax_acc_name: snax_forge_<design>` (the tag: the platform's `accelerator_slot` and the design's name), the slot's `bender_target` dropped, `snax_tcdm_ports` (every set's channels), `sparse_interconnect_config`, `snax_disable_csr_manager: true`, `snax_forge_rtl: "rtl/files.f"` (the RTL's file list in snax-forge's bundle, for snax_cluster; this repo ignores it), `snax_streamer_sets` (per accelerator in order: its `name`, `snax_streamer_cfg`, a `$ref` to its streamer file, `snax_num_rw_csr` and `snax_num_ro_csr`, its own read-write and read-only CSRs, STATUS and BUSY_COUNTER per group the latter) and `snax_datapath_cfg`, a `$ref` to `accelerator.json`.
- `snax_forge_<design>_streamer_<set>.hjson`, a set's streamer file: its streamer template lowered for the design point (readers its accelerator's input ports in the BRM's port order, writers its output ports), each mover's `spatial_bounds` in 64-bit words (`[S_0 / k, S_1, ...]`, k the elements of the port's dtype a word holds) and its `num_channel` their product.
- `accelerator.json`, the accelerators' one description: `design_point`, `tag` and `accelerators`, each with its `name`, its outer `inputs` and `outputs` (its set's readers and writers) and its groups, each with START, JOBS, STATUS, BUSY_COUNTER, its units (datapath `SimdLanes`, `TreeAccumulate`, `Mac`, `SerialAccumulate` or `LaneAccumulate`, each port's `dir`, dtype and lanes, `opType`, `params`, latency, II and span, a fold's JOB_BEATS) and its links (`from`, `to`, `depth`), and the CSRs' offsets, which the standard composite takes (`snax/snax_cfg.py` reads and checks it, `snax/snax_accelerator.py` builds a streamer `streamer_<set>` per set, a shell per group and its unit, or for a linked group one component `group_<group>`).
- `include/`: the headers a program drives it with: per set `streamer_<set>_csr_addr_map.h` (snax_cluster's streamer header, its macros prefixed `<SET>_`: `ACC_BASE_PTR_READER_0_LOW`, `VMUL_STREAMER_START_CSR`) and `<set>_csr.h`, its accelerator's CSRs by their C§17 names (`ACC_RW_START`, `ACC_RW_JOBS`, `ACC_RW_JOB_BEATS`, `ACC_RO_STATUS`, `ACC_RO_BUSY_COUNTER`; with several groups the group's name after the access, `DOT_RW_VMUL_START` ... `DOT_RO_VSUM_BUSY_COUNTER`), and the runtime's view of the cluster (`snitch_cluster_cfg.h` and `snitch_cluster_addrmap.h`, as snax_cluster's templates render them from the cluster file).
- `main.c` (GEN2a, FLOW3, snax-forge D135): the program, the design point's task list on snRuntime: `mcycle` read at main's entry, each step on the core that owns its component, a barrier where another core goes on, each accelerator task's counter stored after its wait, then `forge_check()` on the accelerator's core: `mcycle` read first and `forge cycles:` printed (the program's window), then the self-check, every output against its golden and one `forge counter <task>:` line per accelerator task; main returns the error count. No task marks. The generic app `sw/apps/forge/` builds it.
- `data.h`: its data, from snax-forge's datagen: the inputs from the kernel's `make_inputs` (seed 0), each output zeroed with its `<name>_golden` from the reference executor, each array padded to whole DMA beats and aligned to one.
- `manifest.json`: the design, the design point, the bound graph's symbols, the cluster file (`cluster`), the files, the program (`main.c`), the unit's trace path (`snax_acc0/unit`; with several groups `snax_acc0`; a linked group's `snax_acc0/group_<group>`), the CSR layout (`streamers`: per set its name, first and last streamer CSR and trace path `snax_acc0/streamer_<set>`; `accelerator`: each own CSR's header name -> its number) and each accelerator task's beats and CSR values (its group's JOBS, JOB_BEATS), with several groups also its unit's trace path (`snax_acc0/unit_<unit>`).

Every hjson and C file starts with a comment naming the design point; the rest of an hjson file is JSON, which hjson reads. `accelerator.json` is plain JSON, its `design_point` key naming the source.

## Refreshing a folder

From a snax-forge checkout next to this one (snax-forge README, "Refreshing a fixture"), the folder cleared first (gen-gvsoc leaves a file it no longer writes in place):

    pixi run sandbox recipes/elementwise/vecadd.json
    pixi run design out/sandbox/vecadd/2_bind.snaxdfg --platform platforms/snax_forge.json
    pixi run gen-gvsoc out/design/vecadd/design_point.json --out ../snax-gvsoc/forge/vecadd

(the same with every folder's recipe; the design step reads the sandbox's last step, `out/sandbox/<design>/<n>_<transform>.snaxdfg`: the recipes of `matadd`, `rowsum`, `rowsum_serial` and `rowsum_3x7` have three steps, `dot_1`'s four, the last `4_bind.snaxdfg`, `dot_1_enc`'s five, the last `5_encapsulate.snaxdfg`; `dot_2` and `dot_3` end in `5_link.snaxdfg`, `dot_4` to `dot_6` in `6_link.snaxdfg`, `matvec_1` in `7_encapsulate.snaxdfg`, `matvec_2` and `matvec_3` in `7_link.snaxdfg`, `matvec_4` to `matvec_6` in `8_link.snaxdfg`, `rowsum_2` in `4_bind.snaxdfg`, `matvec_seed` and `matvec_seed_serial` in `8_encapsulate.snaxdfg`; `rowsum_2_padded` is rowsum_2's sandbox folder written to `out/sandbox/rowsum_2_padded`, its design step with `--set memory.passes.layout=padded_rows --out out/design/rowsum_2_padded`), then commit the folder as written and bump snax-forge's submodule so its test compares against it. `make regress` runs every folder with the generic app, so a new folder needs nothing else.

## How it runs

`make regress` runs every folder as `forge.<design>` (`tests/snax/regress.py`): the generic app builds its `main.c` and a runtime against its two cluster headers (`make -C sw/apps/forge DESIGN=<design>`), the installed `snax_hjson` runs it on the folder's cluster file (`--param hjson=`) with the traces `manifest.json` names, and each `forge counter` line must equal its unit's run; the streamers' traces (`snax_acc0/streamer_<set>`) go to the class check. No model is compiled (D134): vecadd's folder runs on the build's platform tree, the others on the JSON config, with gvrun's warning.
